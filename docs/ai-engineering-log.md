## Task 4: Implement redirect, click analytics, and expiration behavior

- **Intent:** Resolve `GET /{code}` to a stored destination, record one click only for an active mapping, and redirect with HTTP 302.
- **Requirements implemented:** Unknown and expired mappings return sanitized ProblemDetail 404 responses; null expiry means active; expiry strictly before the sampled current instant is expired, so equality remains active. Active mappings return their original URL in `Location`. No destination is fetched and no additional analytics or deletion is performed.
- **Constraints:** Preserve the create API, URL validation, generator, schema/migration history, and database configuration. Keep the controller thin and do not return JPA entities.
- **What AI generated:** A dedicated redirect controller/service, UTC `Clock` bean, not-found exception mapping, repository conditional update query, unit/MVC tests, MySQL integration tests, and this traceability entry.
- **What was accepted:** A single repository update increments `clickCount` atomically, with a predicate that only matches an existing code whose `expiresAt` is null or at/after the service's captured time. The service first resolves the row and confirms its expiry, then requires exactly one row to be updated before returning the destination.
- **Concurrency reasoning:** Read-modify-save can overwrite increments when requests concurrently load the same count. `UPDATE short_urls SET click_count = click_count + 1 ...` performs the addition in the database as one atomic statement, avoiding lost updates. The code and active-expiry predicates also make missing/expired updates affect zero rows. No concurrent load test was added; the MySQL integration test exercises repeated successful service redirects and unknown/expired rows.
- **Expiration reasoning:** The service uses one injected `Clock` instant for lookup validation and the conditional update. The update rechecks expiry to cover a mapping that becomes expired between the read and write. `Clock.systemUTC()` is the production default, and unit tests use a fixed UTC clock to cover just-before and exact-expiry behavior.
- **What was rejected/changed and why:** No scheduled cleanup, personal tracking fields, destination fetch, additional schema change, retry loop, dependency, or broader exception hierarchy was added. The result is the original URL string, keeping persistence data out of the controller contract.
- **Tests and validation:** `git diff --check` passed. Focused `mvn -Dtest=ShortUrlRedirectServiceTest,ShortUrlControllerTest,ShortUrlRedirectIntegrationTest test` passed (16 tests, 0 failures/errors/skips). Full `mvn test` passed (38 tests, 0 failures/errors/skips). Both Maven runs used the `test` profile against the existing local MySQL database with credentials supplied only as process environment variables. Logs show Flyway successfully validated the existing V1 migration, the schema was current, and Hibernate initialized the EntityManagerFactory with schema validation; no migration/schema change was needed.
- **Trade-offs and limitations:** Each successful redirect performs a lookup and an atomic write, prioritizing correct aggregate counts over redirect read throughput. The counter update can become a write hotspot at high traffic; distributed counters or asynchronous aggregation are outside this simple MySQL-backed scope.
- **Engineer review/sign-off points:** Review root route behavior relative to any future root-level endpoints; confirm expiry equality is considered active; confirm the intended extra expiry predicate in the update; and review whether redirect-count write load is acceptable for assessment scale.
